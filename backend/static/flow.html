① 總覽：資料從哪裡來、到哪裡去

桶上的 Pi 4 量數據並判斷閘門，上傳到伺服器；伺服器決定桶子狀態，再推給市民地圖、LINE 和清運調度台。

② 感測數據 → 桶子狀態

每一輪：量 9 次超音波取中位數、讀 15 次重量取中位數 → 判斷遮擋 → 更新 LCD → 上傳 → 伺服器分級。

③ 視覺閘門：投入口看到什麼 → 擋板怎麼動

相機每秒判斷數次，同一結果要連續 2 幀才動作，避免誤判。Demo 劇本模式用預錄的偵測結果驅動同一套邏輯。

④ 地面垃圾：外溢還是違規傾倒？

相機同時看桶邊地面，每 60 秒算一次垃圾覆蓋率。伺服器再用桶的滿度判斷原因（融合判斷）。

flowchart TD
  A["地面區域覆蓋率"] --> B{"連續 2 次 ≥ 5%？"}
  B -- 否 --> X["不回報"]
  B -- 是 --> C["上傳 ground_waste
（15 分鐘內不重複）"]
  C --> D{"伺服器查這個桶的滿度"}
  D -- "≥ 90%" --> OV["桶滿外溢 overflow
→ 該加收"]
  D -- "< 90%" --> ID["違規傾倒 illegal_dumping
→ 桶沒滿卻丟地上"]
  D -- "沒有資料" --> UK["地面垃圾（原因不明）"]
  OV --> E["調度台紅色警示
派車時列為必收"]
  ID --> E
  UK --> E

⑤ 清運派車：哪些桶要收？

調度台按「產生路線」時，只收需要收的桶，用 OR-Tools 算最短路線，並和「固定排程繞全部桶」比較節省多少距離。

flowchart TD
  A["每個桶"] --> B{"有未處理的
外溢 / 違規傾倒事件？"}
  B -- 是 --> M["必收"]
  B -- 否 --> C{"已滿？"}
  C -- 是 --> M
  C -- 否 --> P{"依填滿速度預測
N 小時內會滿？"}
  P -- 是 --> M
  P -- 否 --> Q{"快滿 或 感測被擋？"}
  Q -- 是 --> S["順路收 / 順路檢查"]
  Q -- 否 --> K["這趟不收"]
  M --> R["OR-Tools 規劃路線
（容量限制、多車）"]
  S --> R
  R --> V["調度台顯示路線
動態 vs 固定排程 節省 %"]
